# Automatic app-support routing

`openrouter_decision_model` is optional and defaults to `""`. Empty keeps the existing 15-second chat-model handoff triage unchanged. To opt in, configure an OpenRouter Decisions model alongside `openrouter_api_keys`, for example:

```json
{
  "openrouter_decision_model": "perplexity/pplx-decider-v1.2"
}
```

This router handles unprompted messages in the configured guild's app-support channel. The answering and evidence rules below also apply to explicitly addressed app-support requests. Explicit `.note`/`.notes` and slash commands still display full authored notes. Clearing the setting and restarting rolls back to legacy triage. There are no new dependencies, tables, migrations or persistent routing statistics.

## Routing

The client posts to `https://openrouter.ai/api/alpha/decisions`, not chat completions. In one request it asks two independent questions:

- `should_answer` uses Noul to identify an information request or unresolved problem about Metrolist or Metrobot.
- `route` uses Choice to select an eligible saved note, `agent` or `none`.

Neither question assumes it can read the other's answer. Both exclude chatter, keyword-only mentions, reactions, thanks, advice to others, staff coordination, human-directed conversation, donation proof and staff-only role/access requests. There is no keyword-triggered auto-answer rule. Bots, webhooks, other guilds/channels, command prefixes (`.`, `!`, `/`), mentions of other users and replies to humans are filtered before classification. Replies to this bot are allowed, including known retained bot replies whose parent is unavailable in the event; unknown reply targets are ignored conservatively.

An automatic reply requires `should_answer >= 0.80`, a route other than `none`, and an available chat model. At a winning note probability of at least `0.85` and a margin of at least `0.20`, the router supplies that note to the agent through an actual eligibility-checked `get_note` lookup. This avoids asking the model to rediscover the selected reference. Its full rendered tool result and provenance reach both generation and checking; a match never bypasses the answering agent. All positive routes generate a concise answer from applicable evidence, not a full-note dump. Only the delivered answer is remembered as the assistant's reply.

A clear request with an uncertain note match goes to the existing constrained support agent. The `agent` route does the same, without another chat-model triage pass. The agent uses a separate support prompt, without the casual-chat prompt override or shared memory. It can use relevant notes, verified support-skill answers, issue-search results and `get_metrolist_status` for current releases. Issue-search titles and closure status do not establish a diagnosis or a released fix; an empty or partial search does not prove there are no active reports. Unread attachments are explicitly identified as unknown, and destructive troubleshooting is not offered as a generic fix. These support-agent rules also apply to explicitly addressed requests in app-support. Support compaction cannot write to shared memory. Busy state stays silent. After an automatic clear request enters the agent, a lookup or evidence-check failure sends a fixed retry notice instead of an unchecked draft. Explicitly addressed requests use the same neutral service-error notice as other bot chat, even if the topic is casual. The notice does not claim that a particular lookup was needed. Cancelled or deleted requests send nothing. A low request probability, `none`, invalid routing responses and router API errors still stay silent. API failures never trigger an unchecked chat-model fallback. The evidence request also checks independently whether the answer actually uses relevant facts from the last retrieved note. A `note_used` probability of at least 0.95 enables the Components V2 **More from this note** button. Merely retrieving a related FAQ, asking a clarification or answering solely from a setup guide does not justify a note button. Clicking opens the current full note privately for that user, using the existing renderer and FAQ selectors; it does not replace or expand the public answer. Deleted/renamed notes report unavailable. If Discord rejects the answer's components, fallback sends the same answer, never the full note. Explicit note commands remain unchanged.

When Decisions is configured, every support-agent draft, including note excerpts, receives an evidence check against the user's conversation, this run's named tool results and the support skill. Sending requires a grounded-answer probability of at least 0.95. A rejected draft gets at most one short rewrite, checked again. The retry must make a fresh tool lookup before synthesis. The evidence check still decides whether that result supports the answer. It reserves retrieval and answer rounds even after an initial final-round rejection, with at most six tool rounds within the existing request deadline. API errors and malformed verdicts fail closed without a rewrite. Rejected drafts are never delivered or retained as user-visible conversation. The agent and checker receive the full rendered note snapshot, including text beyond the usual tool truncation limit; later note edits cannot replace that evidence or the checked answer. An explicit More-button click separately reads the current note. Requests too large for the Decisions API fail closed. This is a probabilistic safeguard, not a factual guarantee, and can suppress valid answers. Without Decisions configured, legacy support has the isolated prompt but no independent answer check or automatically generated note-reference buttons.

The embedded references are `support_rpc.md`, `support_login.md`, `support_scrobbling.md`, `support_playlists.md` and `support_discovery.md`. Generation keeps the small support core and retrieves full guides through `load_support_guide`, without keyword-based preloading. `load_skill` and all five guides remain discoverable for novel wording and follow-ups; loading one reference does not hide the others. `load_skill(name=support)` returns only the small triage core; it does not bundle all setup guides. Tool descriptions explain when to retrieve each skill/guide. The evidence checker intentionally receives the full trusted reference set through a separate loader. Retrieval is not factual authorization or a replacement for checking. Support generation and compaction omit Discord profile/channel metadata and retain timestamps. These source-verified references distinguish standalone Android v13.7.0 from pinned Android/KMP development snapshots. Casual chat also receives the scoped project reference, even with a prompt override or contradictory shared memory, and can retrieve all five guides. With Decisions configured, a small semantic classifier routes casual app-fact/setup requests and corrections through the same isolated support prompt and evidence gate. It runs before compaction, using the current request, up to 20 prior bounded turns and a retained summary when present; it receives no shared memory or Discord profile metadata. A conservative probability threshold of 0.20 favors the checked path for ambiguous app follow-ups. Non-app chat keeps its ordinary prompt and does not load the full guides. Classifier API errors or invalid verdicts fail closed before generation, so Decisions outages also temporarily affect ordinary chat. Clearing Decisions restores legacy ungated casual behavior. KMP source access is not assumed public. They cover actual account-menu entry points, authorization, switches and narrowly verified internals. Development source is not evidence of released-build availability. Common verified steps need not prompt unnecessary version questions; materially different flows must be scoped or clarified. Setup questions must not be answered with merely related troubleshooting FAQs. Guides were source-reviewed, not device-tested; update their pinned provenance when rechecking changed app flows.

The thresholds were checked against labeled replays, not calibrated into accuracy guarantees. A high probability does not prove a diagnosis or fix. This change adds no crash diagnoses or data-clearing instructions.

## Note opt-in and changes

The catalog is rebuilt from `Notes.DB.ListNotes()` on every classification. Only notes with a nonblank `short_desc` are eligible as automatic support sources. Blank-description notes remain manual-only. Explicit note commands are unchanged.

Descriptions are routing criteria, not answer bodies. Write a short, precise scope such as "How to install nightly builds from official releases", including important exclusions if needed. Do not give joke, irrelevant or media-only notes support-routing descriptions. Back up the database before backfilling existing descriptions; the binary never seeds or overwrites production notes. The separately authored update and its source review are documented in [support-notes.md](support-notes.md). Review descriptions and the actual note contents before enabling routing.

Each note gets an opaque request-local option ID (`n0`, `n1`, ...). Names such as `agent` or `none` cannot collide with router actions. Additions, deletions and renames appear in the next request. The agent reads current note content rather than treating the classification's description as evidence. Automatic retrieval rejects missing/manual-only notes, and delivery rechecks that its referenced note still exists and remains opted in. A changed description or body must be evaluated from the retrieved source, not the earlier catalog.

## Bounds, privacy and failures

- Automatic app-support note routing sends Decisions text only: up to 4,000 UTF-8 bytes of current text, a visible referenced bot parent (up to 1,500 bytes), and at most four relevant retained user/assistant turns (1,000 bytes each). That router excludes earlier summaries, profile/ID metadata, emoji catalogs, reasoning and persistent memory.
- The casual app-guidance classifier uses the same current/parent bounds plus up to 20 prior user/assistant turns (1,000 bytes each) and the retained summary (2,000 bytes). It does not load note bodies, setup guides, shared memory or profile metadata; retained conversational text may itself contain names. Classification occurs before compaction; routed support compaction/generation gets timestamp-only Discord context. Every classified support answer receives the existing independent evidence check. Unrelated chat does not load that checker reference set. This adds a Decisions dependency and one bounded classification call to casual requests; failures do not fall back to potentially ungrounded app advice.
- This release accepts text only. Attachments are neither fetched nor classified, their filenames are not evidence, attachment-only messages are ignored, and images are removed from automatic agent handoff messages. Image support would require bounded base64 data URLs under the Decisions multimodal contract, not remote attachment URLs.
- Provider preferences always include `data_collection: "deny"` and `sort: "latency"`. Configured answering models now retain these preferences and require supported request parameters too; Default-Qwen reasoning is disabled. Explicit prompt-cache hints are limited to documented supporting models and the built-in base prompt; custom prompts and appended shared memory are not explicitly marked for caching. No fixed cross-user session ID is sent to chat completions, and no extra session/user tracking identifiers are sent to Decisions. The selected provider still receives the bounded message text; do not interpret this setting as local inference.
- Requests and responses are capped at 64 KiB. Catalogs over 128 eligible notes, names over 256 bytes or descriptions over 640 bytes fail closed rather than classifying a partial catalog. Message fields are UTF-8-safe truncated at their bounds.
- Two independent Decisions slots do not consume the three general-AI slots. Total classification timeout is four seconds, including at most one retry, a 100 ms pause and key failover. Each attempt has a two-second timeout. Retryable failures are transport/read failures, HTTP 408/429/5xx, and 401/402/403 when another configured key exists. Other HTTP failures and malformed responses are not retried. Redirects are refused.
- Missing/wrongly typed answers, unknown IDs, absent/null/nonfinite/out-of-range probabilities, non-normalized distributions (outside 0.01 rounding tolerance), a chosen option that is not a probability winner, and malformed/oversized envelopes are rejected. Provider `confidence` is not substituted for the selected option's probability.
- A bounded in-flight/seen message map suppresses concurrent duplicates and retains completed decisions for ten minutes. Generated answers use the normal per-user agent cooldown and concurrency slots. There is no longer a ten-minute same-note cooldown: a different follow-up can need another part of the same source. Failed classification/delivery, including busy or failed agent handoffs, releases the seen entry so a later event can retry after normal rate limits. Successful delivery and intentional agent silence remain deduplicated. Rejected drafts do not mark an event complete, so the same event can retry after normal rate limits. Expired entries are pruned on activity; maps hold at most 1,024 entries and refuse new work when full rather than evicting active requests. State is in memory and resets on restart.
- Deletion events cancel registered requests before audit-log filtering; a bounded ten-minute tombstone map and the existing context-reset visibility guard suppress late results. Delivery rechecks visibility under the existing reply lock. A send already in progress cannot be recalled by cancellation.
- Unlinked follow-ups use the existing same-user, same-guild, same-channel conversation context (24-hour in-memory expiry), while classification receives only its bounded recent text. Users do not need Discord's Reply button. A follow-up supplying requested versions or error details can continue support; thanks and resolved problems still route to silence. No timers or unsolicited follow-up messages are added. Explicit Decisions-enabled support requests also claim the message ID to prevent duplicate events from replacing an active request or posting twice.
- Decision logs contain the intended action, opaque Discord message ID, selected note name, answer/route probabilities, margin, elapsed classification time, resolved model and reported cost when available. Intended action is not a delivery counter: cooldown or visibility checks can still suppress it. Failure warnings omit upstream error strings. No message bodies, profiles, credentials, upstream error bodies or request URLs are logged by the Decisions client/router.

## Verification and rollout

Offline checks:

```sh
go test ./...
go test -race ./discord ./cmd ./config
go vet ./...
```

`discord/testdata/support-routing.json` contains synthetic labeled help requests and nonrequests, including short follow-ups and support chatter. Tests inject synthetic probabilities and use local HTTP servers: they verify wire contracts, validation, routing policy, grounded excerpt delivery, private note access, setup-guide availability, context continuation, dynamic catalog handling, deduplication, cooldown, cancellation and fail-closed behavior. They make no model API calls and do not measure classifier accuracy.

Before production enablement, privately replay a representative, manually labeled sample against the actual request instructions and current note descriptions. Include chatter, staff advice, donation proof, human-directed replies, bot follow-ups and ambiguous requests, not just easy questions. Check false replies, selected-note correctness, abstentions, tail latency and reported `usage.cost`; inspect both Noul and Choice results. Keep real HAR exports, selected message text, API keys and replay outputs outside git and ordinary logs. Recalibrate after changing models, instructions, descriptions or thresholds. `TestSupportDecisionsLive` is an opt-in paid replay. It uses a temporary database and never connects to Discord or opens the production database. Supply `METROBOT_DECISIONS_LIVE_CONFIG`, `METROBOT_DECISIONS_LIVE_NOTES`, `METROBOT_DECISIONS_LIVE_CASES` and `METROBOT_DECISIONS_LIVE_REPORT`. The config supplies OpenRouter keys and the model; `METROBOT_DECISIONS_LIVE_MODEL` can override the model for comparisons. Notes are a JSON array with `name`, `short_desc` and `content`. Cases have `id`, `message`, optional `parent` and `conversation` (role/content pairs), and an `expected` array of acceptable actions or note names. Run `go test ./discord -run '^TestSupportDecisionsLive$' -v`. It reports every mismatch without changing labels or sending public replies. The synthetic evaluation cases are in `discord/testdata/support-decisions-eval.json`.

Historical baseline before excerpt replies and setup guides: on 25 October 2026, the revised prompt on Decider Flash V1.2 matched 77 of 84 synthetic cases. Decider V1.2 matched 82 of 84 with the initial 0.90 request threshold. The latter took a median 292 ms and cost $0.00156260 for that run. With the request threshold set to 0.80, a separate 60-message HAR sample matched 54 labels: four requests stayed silent and two went to the agent instead of directly to a note. It sent no incorrect notes and routed no labeled chatter to the agent in that sample. Median latency was 292 ms, p95 was 549 ms, and the run cost $0.00112562. A final rerun at the 0.80 request threshold matched 83 of 84 synthetic labels. The remaining case went to the agent instead of directly to the update note, so it did not post a wrong note. Median latency was 296 ms, p95 was 378 ms, and the run cost $0.00156260. These samples do not establish channel-wide accuracy. Keep the conservative note threshold and recheck after changing the model or catalog.

`TestSupportAgentLive` exercises the answering agent separately, including router-selected note fixtures, unrelated RPC FAQ versus setup intent, standalone Android/KMP setup flows, invented nightly status, unread images, issue-closure overclaims, destructive troubleshooting, current-release questions and valid note/Firefox answers. Set `METROBOT_SUPPORT_LIVE_CONFIG`, `METROBOT_SUPPORT_LIVE_NOTES` and `METROBOT_SUPPORT_LIVE_REPORT`, then run `go test ./discord -run '^TestSupportAgentLive$' -count=1 -v`. It makes paid chat/Decisions calls and read-only public GitHub requests, uses a temporary DB, and never connects to Discord. The config needs both chat and Decisions model settings. Reports contain drafts, verdicts and final answers: keep them private and review them manually. Phrase assertions only catch the named regressions; silence and a passing test do not establish answer quality. The harness also includes six casual-chat cases based on login denial, corrections and KMP platform confusion, with deliberately false synthetic memory. Those cases require manual factual review even though classified app guidance now uses the support evidence gate. The harness also covers unrelated casual chat and KMP platform minimums/package identity. Reports include initial prompt character counts (not token counts) and model-call counts.

A later 25 October support-agent check rejected all eight sampled bad production answers, two unsafe prompt-only replay drafts and a spoofed release claim inside a note, while accepting four safe controls (15/15 labels). A nine-case agent replay delivered eight answers and abstained on an ambiguous crash case; its safety assertions passed. Four separate continuation cases routed both unlinked information follow-ups to the agent and both thanks/resolved messages to silence. These small, reviewed samples are not a guarantee against hallucinations or false abstentions. Unanswered support questions now remain in bounded RAM context after a rejected draft or failed attempt. A follow-up such as "answer" can refer to that question without retaining the rejected draft or starting ambient replies. Routing treats a request to answer a retained question as a continuation, not a command to ignore. Pending source IDs follow replies and referenced continuations so deletion removes derived context. At 40 pending origins, retention drops old history rather than forgetting its deletion sources. Intentional silence clears provisional pending state; post-rejection silence remains retryable and keeps the unanswered question. Restarting still clears in-memory conversations, so pre-restart support threads are not automatically restored.

### Excerpt/setup verification and private model comparison

The local excerpt/button change passes whole-repository offline tests, race tests and vet. Independent code review found and resolved ambiguous-send duplicate retries, conflicting named-staff guidance and unused notes being offered under clarifying answers. Private More responses suppress mentions without changing manual slash-note mention policy. API-contract tests cover private current-note access, unavailable notes and suppressed mentions; no coded UI tests or public Discord test posts were added.

### Subsequent Qwen context experiment (not deployed)

Three paired 27-case runs compared the earlier full-guide generation path with selective context. The first run's median initial prompt/context length fell from 27,315 to 12,708 characters, not tokens. Delivered-text counts were 19/21/22 for the baseline and 18/19/21 for the experiment; these include answers with manual-review problems, not verified usefulness scores. Later pairs used concrete prompt examples. Quality was still inconsistent, so these measurements do not justify deploying the broader patch.

Six casual-chat regression cases were then replayed three times with synthetic false memory. The local fix stopped the repeated login denials in those samples, but manual review still found invented refresh steps, unsupported feature-introduction/version claims and a leaked internal tool name. Passing the replay's structural assertions did not establish factual correctness. The production binary and models were therefore retained. A separately authorized, backed-up production memory correction supplied scoped login/playlist/platform facts and corrected verified stale app claims; this is not a guarantee against future hallucinations. No public Discord test messages or device/account sign-in checks were performed.

### Earlier reference/checker evaluation

The updated evidence check matched 27 labels (17 unsafe drafts and 10 safe controls), including source-provenance spoofing, mixed login flows, a dialog confused with its website link, song-duration/listening-time confusion, and an invented proof-submission location. Setup/troubleshooting routing plus an unlinked variant follow-up matched 9/9 labels. The latest broad Qwen agent replay was **not clean**: 14 replies, four abstentions and one agent error across 19 cases; generic RPC setup remained inconsistent. These failures are not hidden by the offline checks.

At the user's request, a private seven-case comparison kept the same guides, evidence model and 0.95 threshold. GPT-5.4 mini produced six useful answers and abstained on Windows login (median 1.64 s). GPT-5.4 and Claude Sonnet 4.6 each produced seven manually reviewed useful answers (medians 2.48 s and 4.54 s respectively). Timing includes the evidence check. A phrase-only assertion initially rejected both larger models' short, sourced Invisible-status reminder *after valid setup steps*. The assertion now checks the actual regression: a FAQ must not replace setup/clarification or add unrelated FAQ sections. Original failing logs were retained, and saved answers were re-evaluated; this is not a claim that those original test runs passed.

The deliberately mismatched-note fixture allows safe abstention; normal setup fixtures still require a useful answer or clarification. These are small quality samples, not reliability guarantees or device/UI verification. No production model, runtime, notes or account settings were changed, and no changes were pushed or deployed for this work. A model switch needs separate approval.
